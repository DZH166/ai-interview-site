本文件可完整交给后续编码代理执行。审查基线为`d264959142a74bc6de37a06c9321723860819291`，审查证据见[审查报告](审查报告-d264959.md)。若远端已经有后续提交，先确认哪些问题已修，不要把新代码退回此基线。

## 大方向

把现有功能做成一个可靠的学习过程：**写下回答 → 练追问 → 保存真实记录 → 得到合理复习建议 → 导出可使用的材料**。用户在多页切换、刷新、更新题库和恢复备份之后，仍应知道自己答了哪道题、哪次回答已保存、哪些建议已撤销、导出的内容来自哪里。

目前已有349题、15篇文档、Pi Agent及LangChain与LangGraph分类，内容规模足以支持这一轮工作。接下来的主要收益来自记录正确、练习连贯、出口可用。先完成下面的必修阶段，再推进内容深化与性能优化。

4. 给SRS旧备份复活、未来日期文案、追问错配和只答追问导出各写独立用例。对内容升级用响应替换或版本fixture，不修改真实题库来凑结果。
5. 记录每个用例在未修复版本的失败结果、必要事件轨迹与最小输入，注明是否依赖固定时钟或注入错误。
6. 基线现有测试为Node333、Python109、浏览器226，合计668项。重新执行后按机器输出统计，不直接复制这些数作为新结果。

**交付物：** 失败用例、机器可读基线结果、一页问题状态表。条件未满足时不得宣称原问题已复现或已修复。

## 阶段1：阻断跨页写回循环与旧DOM覆盖

1. 拆清四个动作的职责：本地用户编辑、持久化写入、远端数据合并、局部界面刷新。渲染本身不能隐式产生新的业务写入。
2. 合并结果返回真实变更，例如题号、字段或会话集合。处理条数不能用作变更数量；只变化`savedAt`之类元数据不能引起整页刷新。
3. 去掉storage事件到带退出保存副作用的`App.route()`链路。为远端更新提供不触发flush/save的刷新方式。
4. 为编辑控件维护dirty状态与编辑基准版本。未编辑的旧textarea不得提交；正在编辑的同字段遇到远端更新，保留本地输入与远端值，不静默替用户选择。
5. 跨页更新其他题目时，不丢当前焦点、选区、滚动位置、已展开答案和输入法组合输入。
6. 去重重复事件，避免同一远端版本反复通知。必要的保存失败提示仍应保留，不能用吞掉错误停止循环。

**验收：** 两页同步稳定后静置至少3秒，业务写入、路由和提示计数不再增长；聚焦笔记框后不抢焦点；A未编辑旧笔记时，B成功保存的新笔记在A、B、磁盘和刷新后均保持新版。A真正在编辑时，两版内容均能找回，冲突处置有明确结果。

## 阶段2：把删除、终止和并发冲突纳入记录模型

1. 给全局清空定义明确版本或删除标记。旧页清空前的快照不能越过此边界；清空后新写的记录可以正常同步。
2. 给模拟面试分配稳定sessionId，区分draft、completed、abandoned。完成和放弃都有可比较的终止版本，旧draft不能使终态倒退。
3. 区分被动接收远端旧状态和用户主动恢复备份。前者不得复活删除；后者需要明确恢复语义，保留新旧数据来源，避免把恢复动作伪装成新作答。
4. 同一会话重复完成、重复恢复、重复接收事件都不得制造第二条练习历史。同一记录的同毫秒修改要有稳定决胜规则，不能取决于事件到达顺序。
5. 不要把“保存前再读一次localStorage”称为并发事务。先验证同时写、乱序事件、旧页恢复和关闭前保存，再选最小实现。
6. 可以评估协作锁、单写入协调或可合并操作记录，但要写出选择理由与支持范围。如果引入异步写入，逐一迁移依赖`saveNow()`同步返回值的调用点，并保持失败回滚与重试。
7. 不支持所选协调机制时提供明确降级，不能在实现只保证单页时仍宣称多页安全。

**验收矩阵：** A/B分别清空后对页写入；清空后关闭再打开旧页；完成后对页回放旧草稿；放弃后旧备份恢复；两页同时改不同题；两页同时改同字段；同时间戳；事件乱序；重复事件；写盘失败；刷新及导出→清空→恢复。每项核对A内存、B内存、磁盘和重新打开后的状态。

HTML标准要求应用不要假定localStorage有跨执行环境的锁；Web Locks提供异步的同源协调能力，并有安全上下文等适用条件。这些资料用于设计判断，不构成自动选型结论。[Web Storage规范](https://html.spec.whatwg.org/multipage/webstorage.html#the-localstorage-attribute)、[Web Locks说明](https://developer.mozilla.org/en-US/docs/Web/API/Web_Locks_API)。

## 阶段3：修正SRS清除语义和练习信号

1. 状态、排期和撤销操作要作为一致的记录处理。较旧备份不得补回较新状态已撤销的srs。
2. 建议队列增加明确的有效性条件：未练习、已撤销、缺失或非法排期不能产生建议。不要只排除weak/review后把剩余所有记录都交给due判定。
3. 修正`dueLabel`：先判断是否真正到期，再生成未来日期；文案计算与队列判定不能相互矛盾。
4. 明确日历语义，补同一毫秒、未来1毫秒、23小时、24小时、跨午夜、时区变化测试。未来不到一天可以显示今天/稍后或具体时间，但不能显示已到期。
5. 一次真实练习信号使用稳定事件身份。同一轮同一题重复点击同一复盘按钮，不应当成多次独立练习把间隔连续推大；另一轮真实作答应正常推进。
6. 定义更改自评的行为：同一练习内修正一次评价，是替换该次信号还是新增事件，必须有一致实现和可解释记录。
7. 保持算法只建议、手动状态优先。不要因为加入排期而修改用户已经保存的掌握状态，旧记录没有可靠信号时不猜历史练习。

**验收：** 旧备份不能复活撤销排期；三种恢复/同步入口行为一致；未来文案与队列一致；重复点击不重复排期，新轮次会正常推进；失败保存不产生已经完成的复习证据。

## 阶段4：追问具有身份、版本与历史快照

1. 为追问建立稳定身份。优先沿用可信源ID，补充时保证新增、重排、删除不改变其他追问身份；不能仅使用数组下标。
2. 新草稿保存追问ID、当时题面、必要参考快照和内容版本。用户回答始终关联当时作答对象。
3. 内容更新时，未完成会话继续以已保存快照展示；如允许切换到新版，必须明确区分旧作答和新题面。
4. 已完成轮次不依赖当前题库重新推导追问文字。题目删除、追问减少和来源内容变化都不能删除历史回答。
5. 迁移旧的`fu[index]`草稿。只有存在足够版本依据时才能确定映射；不确定则保留旧回答并标记需核对，不得假装已经知道原题面。
6. 为主问题也建立最小内容版本上下文，避免后续导出把新答案当成当时看到的参考。区分“作答时快照”和“当前参考版本”。
7. 扩展备份校验：合法旧格式可恢复；新字段类型错误要整体拒绝或明确隔离，不能在界面中途崩溃。

**验收：** 重排、插入、删除、改写追问后刷新旧草稿，回答仍归原问题；新旧备份往返保留身份；已完成历史及导出不受当前题库顺序影响；无法确定的旧映射不会被静默猜测。

## 阶段5：统一练习完成与导出资格

1. 把“有真实作答”定义为可共享的判定：主回答或任一追问有非空文本。仅揭示参考、打分或浏览不满足这个条件。
2. 修复只写追问不能导出的阻断，覆盖完成页、历史轮次、首页快捷出口和Markdown/打印HTML。
3. 当前“今天是否练过”、可导出按钮、完成摘要和统计使用同一事实定义；若统计需要区分主回答与追问，清楚显示两个数量，不把它们重复计为两道主问题。
4. 保持只看过参考但没写的追问如实标注；不会因为它有`revealed=true`就生成“我的回答”。
5. 完成页展示实际追问回答和题面快照，用户不用先下载文件才知道保存了什么。
6. 导出明确区分个人回答、个人笔记、当时参考、当前参考、融合补充。处理长文本、换行、Markdown、HTML字符及恶意字符串。
7. 保持真实下载验收：检查文件内容，而不只看函数返回ok或页面出现成功提示。

**验收矩阵：** 仅主回答、仅追问、两者都有、只有空格、仅揭示、旧格式轮次、当前题库缺失、题面更新、保存失败后重试。只含参考且无真实作答仍拒绝，确有追问回答必须能带走。

## 阶段6：让Anki出口有明确使用契约

1. 选择并记录一个完整方案：三字段自定义笔记类型，或者明确适配现有Basic类型。说明题号、正面、背面分别如何映射。
2. 保留稳定题号用于更新匹配，不把自定义ID冒充Anki内部GUID。提供笔记模板或准确的字段设置步骤。
3. 导出说明包含所需笔记类型、字段映射、HTML选项、重复导入行为。CSV头只能做它实际支持的配置，不声称能自动创建任意模板。
4. 验证中文、引号、换行、代码、尖括号、超长内容；确认卡片正面是问题，背面是答案，题号不会意外成为唯一正面。
5. 二次导入同题号时按设计更新，而不是制造重复卡片；更新不得无意清空用户已有复习安排。
6. 在当前环境可用时，用隔离Anki测试配置实际导入并查看正反面。不可用时完成CSV解析、样例与导入说明，报告“真实Anki导入尚未验证”，不能拿下载测试替代。

**交付物：** 可复用导入模板/说明、样例文件、导入前后字段结果。以官方[文本导入手册](https://docs.ankiweb.net/importing/text-files.html)核对文件头、映射和更新规则。

## 阶段7：搜索缓存按内容版本失效，并保留可测性能

1. 保留静态与动态分层，但给静态层明确的内容版本或library revision。题量相同不等于内容相同。
2. 定义哪些操作更改内容版本：题库新增/替换、章节变化、概念或项目定义变化、完整恢复、未来热更新。仅个人笔记编辑不应触发静态重建。
3. 以原始未缓存构建或独立预期结果作对照，验证检索命中、锚点、旧内容消失、新内容出现，不能只检查构建次数。
4. 追问身份和会话快照进入索引时，结果必须标明来源及真实轮次，点击落到具体回答，不只打开主题顶部。
5. 对349题真实数据和有说明的扩大量级样本，分别测构建、查询、动态更新时间与内存。记录环境、样本规模和多次分布，不把一次最好结果作为性能结论。
6. 只有查询本身成为明确瓶颈时才引入倒排或Worker；保持排序语义、中文检索和本地离线能力。

**验收：** 等长内容更新不会命中旧缓存；个人写入不重建静态层；多页同步后新笔记可搜、撤销内容不可搜；查询结果与对照一致。

## 阶段9：校准存储健康度与容量决策

1. 分开记录题目状态、长笔记、模拟回答、追问、项目证据、导入题库和导入文档的体积。
2. 明确界面展示的是序列化字符数、估算字节数，还是浏览器origin配额估计。不能把`JSON.stringify().length`直接当成准确占用，也不能把`navigator.storage.estimate()`解释为localStorage剩余专用配额。
3. 用真实允许的单条长度、轮次上限及导入资料构造压力样本，测写入耗时、失败位置、启动、合并和导出。不要把“每题500字”的单个样本称为极端上限。
4. 若测量证明导入资料确实是容量瓶颈，再先迁移该部分；记录层是否迁移另行依据保存协议和失败恢复复杂度判断。
5. 任何迁移都要有旧格式读取、恢复、重复运行和失败中断测试。迁移不能成为跳过阶段1～5的理由。

**验收：** 存储文案与测量口径一致，满额时输入可恢复，导出成功后可在全新上下文还原。迁移或不迁移都有具体数据支持。

## 阶段10：完整验收与发布

1. 运行与改动有关的用例，再运行完整回归。新增边界用例纳入CI，保持基线问题在旧版本确实失败、修复后通过的证据。
2. 检查JS语法、题库字段、重复度、来源结构、内容审计及两个融合适配器。重新构建并验证构建与缓存戳一致。
3. 做一次真实用户旅程：新建记录→练主题与追问→保存→换页/刷新→双页协作→完成→查看复习→导出→清空→恢复。旧题、Pi Agent、LangChain分类与项目证据功能都要覆盖。
4. 检查窄屏、键盘、输入法组合输入、打印与下载；CSP测试包括实际功能调用。若声明离线可用，实际等Service Worker就绪后断网访问，不能只检查源码里有register字符串。

6. 按有意义的阶段提交，写清问题与结果；推送前确认远端没有新提交需要纳入。不要强推覆盖他人工作。
