# 阶段:多标签页并发与存储健康度(2026-09-13)

## 为什么改了方案(原计划:记录层整体迁移 IndexedDB)

精读全站后发现,整体迁移 IDB 的代价与收益不成立,如实记录测量依据:

1. **体积实测**:极端重度使用(349 题全部 500 字笔记 + 100 轮模拟面试每轮 10 题
   完整回答与追问)的记录 blob ≈ **1.3MB**,远在 localStorage 5MB 预算内;
   真实使用(~2KB 备份)相差三个数量级。配额风险主要来自**导入的题库/资料**
   (`aiiv:bank-extra` / `aiiv:userdocs`),而非记录层。
2. **同步契约是承重墙**:全站 20+ 调用点依赖 `Store.saveNow()` 的**同步**返回值做
   「失败真报错 + 内存回滚」(专项提交、项目运行记录、口述保存、导入回滚)。
   IDB 全异步意味着重写整条错误反馈链——这正是本项目用几百条断言建立起来的部分。
3. **真正挂账的风险是并发**:状态表「诚实边界」写明「多标签页并发写入互相覆盖未测」。
   localStorage 同源共享、每页一份内存副本、后写整份覆盖——会**静默丢数据**。

因此本阶段交付:多标签页写入合并 + 存储健康度;IDB 迁移降级为「若记录体积实际增长到
MB 级再做」的备忘(先迁导入题库,记录层最后动)。

## 实现

| 落点 | 内容 |
| --- | --- |
| `Store.adoptRemoteRecords(jsonText)` | 复用备份导入的**同一套合并规则**(逐记录 `_updatedAt` 新者胜、轮次按内容去重、项目草稿整份判定、pathProgress 晚者胜),把另一标签页写入的记录合并进本页内存。只合并内存、**不回写磁盘**(本页下次保存自然带上,不会形成写回循环);非法载荷整体拒绝 |
| `store.js` 的 storage 监听 | storage 事件只发给非写入方,天然区分「对方的写」;合并后有实际变化才 toast「已合并另一个标签页的修改」并重渲染当前视图 |
| `Store.recordsSizeKB()` + 维护页 | 显示个人记录占用(KB)与 `navigator.storage.estimate()` 的用量/配额估计 |
| 样式/文案 | 维护页说明多标签页行为 |

## 冲突窗口(诚实说明)

本页防抖窗口(250ms)内尚未落盘的击键可能被对方的版本盖掉——笔记每次击键都先进内存,
模拟面试回答 200ms 防抖落盘,真实丢失上限是一次防抖窗口的输入。两页**同时**写同一字段时,
按记录级 `_updatedAt` 新者胜,后写的赢——这与备份导入语义一致。

## 未做(如实)

- IDB 迁移(理由见上;触发条件:记录体积实际逼近 1MB 量级再评估);
- BroadcastChannel 冲突提示(当前 storage 事件已覆盖,不引入双通道);
- 跨设备实时同步(仍然走完整备份 round-trip,这是有意的产品边界)。
