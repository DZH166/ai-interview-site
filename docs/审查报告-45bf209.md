## 四、新发现问题（按严重度）

### P1 — 必须下一轮先修

**N1 专项提交写盘失败仍提示「已保存本次尝试」（错误语义）**

- 证据：用 `Storage.prototype.setItem` 对 `aiiv:records` 抛 `QuotaExceededError` 模拟写盘失败后，页面 toast 依次出现
  `保存失败:本地存储空间不足或被禁用` ×4，**最后一条是** `已保存本次尝试(历史保留;开始新尝试将不显示旧答案)`。
- 定位：`app/js/views-knowledge.js:556-564`（提交 handler 未接收 `saveAttempt` 的落盘结果）、`app/js/views-knowledge.js:772-778`（`saveAttempt` 调 `Store.saveNow()` 但丢弃返回值，仍无条件 `rebuildIndex()`）。
- 同类：`app/js/views-knowledge.js:512-525` 口述草稿保存也未判 `saveNow()` 返回值。
  （对照：项目记录保存 `views-knowledge.js:502-506` 判了，是正确写法。）
- 影响：用户以为记录已保存，刷新后内容消失 —— 数据丢失 + 虚假成功。
- 最小修复：`saveAttempt` 返回 `Store.saveNow()` 的布尔值；提交/新尝试/自评三处按返回值决定 toast 文案与是否 `render(root)`。

**N2 projectDrafts 字段级合并会复活用户主动清空的字段**

- 证据：本地 `projectDrafts['proj-a-model-client'] = {runOutput:'', updatedAt:9000000000000}`，再恢复 `{runOutput:'旧备份内容', updatedAt:1000}` 的旧备份 → 恢复后 `runOutput='旧备份内容'`。
- 定位：`app/js/store.js:502-507`
  ```js
  if (cur[k] === undefined || cur[k] === '' ||
      ((inc.updatedAt||0) > (cur.updatedAt||0) && cur[k] !== inc[k])) { cur[k] = inc[k]; }
  ```
  `cur[k] === ''` 这一支**完全绕过时间戳比较**，无法区分「访问路径页自动建的空壳」与「用户主动删空」。
  注释里写的正是这个意图（"先访问路径页建的空壳不算主动清空"），但实现做不到区分。
- 影响：用户删掉的项目记录会被任意旧备份复活；与「更新的备份才能恢复清空」的承诺冲突。
- 最小修复：给空壳加标记（例如渲染时写 `drafts[pid]._shell = 1`），或记录「用户是否编辑过」的 `_touchedAt`；只在 `_shell` 为真时才走「本地空采用备份」。

**N4 项目D 的「预期输出」与默认运行命令实际行为不一致（教学正确性）**

- `data/projects.json` 中 proj-d 声明：`run = python projects/proj_d/agent.py`，`expected = 10°C→50.0°F 写入真实 report.txt;0°C→32.0°F;缺温度如实报错;检查点续跑只补 2 次调用`。
- 实测（照抄文档命令）：首个场景标题是「完整链:天气(**含温度**)→ 换算 → 报告」，实际输出
  `轮1: get_weather → {"city":"北京","weather":"晴","temp_c": null}` → 终答「天气数据缺少温度字段,无法换算。」**没有换算、没有写文件**。
- 根因：`projects/proj_d/agent.py:111` `temp_c = None`（不带参数即无温度），而场景标题与 `expected` 都假设含温度。10°C→50.0°F 只在**检查点续跑**场景（`agent.py:152`）里出现。
- 影响：学习者照 `run` 命令跑，得到与「预期输出」相反的结果。
- 最小修复：`run` 补参数 `python projects/proj_d/agent.py 北京 10`，或把首场景标题/expected 改成如实的「无温度参数时如实报缺数据」。
- 同类需一并核对：`docs/upgrade-progress.md:126` 也写着「10°C→50.0°F 写真实 report.txt」，与实际默认行为不符。

**N5 旧备份（无 `_updatedAt`）无法恢复或清空 reviewReasons**

- 证据：本地 `PY-001.reviewReasons=['concept']`，导入备份 `{reviewReasons:['exec']}`（无 `_updatedAt`）→ 恢复后仍是 `['concept']`，完全未生效。
  （对照：备份带 `_updatedAt: 9999` 时整套覆盖与显式清空都正常。）
- 定位：`app/js/store.js:589-598`（importRecords）与 `store.js:809-818`（importFull），两处相同：
  `incAt > curAt` 才覆盖，否则仅当 `cur.reviewReasons === undefined` 才补。
- 影响：用旧版本导出的备份恢复，复习原因这一栏永远恢复不了。

**N6 恒真断言未清零，且正好落在这轮重点复验的路径上**

- 定位：`tests/behavior-tests.js:524`
  ```js
  ok('重复恢复幂等', (Store.data.ui.projectRuns || {})['proj-a-model-client'] === undefined || true);
  ```
- 影响：`|| true` 使该断言恒真，R9b 的「重复恢复幂等」**没有任何实际防线**；备份/迁移类回归无法被发现。
- 说明：同文件 `:476` 的 `round-trip: 重复恢复幂等`（`r2.roundsAdded === 0 && ...`）是真实断言，但覆盖的是另一条路径。
- 最小修复：删掉 `|| true`，改为断言 `projectRuns` 条数在重复导入后不变。

**N7 drill-4fix02 参考答案第②条与本机实测不符**

- 参考原文：「②JSON Schema 没有 tuple 类型概念在多数平台的子集里不受支持(数组用 array+items)」。
- 本机实测（pydantic 2.10）：展示代码里的 `tags: tuple[str, ...]` 经 `model_json_schema()` 得到的是
  `{"items":{"type":"string"},"type":"array"}`，**已经是 array+items**，schema 里根本没有 tuple 形态。
  第①条（缺 `additionalProperties:false`）实测成立。
- 影响：本例子根本不涉及「tuple 不受支持」，答案把它列为主因之一属于过度归因（`tuple[str,int]` 定长才会产 `prefixItems`，但展示代码不是这种）。
- 最小修复：把第②条限定为「定长 tuple 会产 prefixItems，才可能不被平台子集接受；本例 `tuple[str,...]` 已是 array+items」。

### P3 — 可延后

**N8 空用户首次打开即落盘 306 条空记录**
`HomeView.getTodayReviewCount()`（`views-knowledge.js:960-965`）对全部题目调 `Store.rec(q.id)`，`rec()` 会建记录。
实测：全新浏览器上下文打开首页，**未做任何操作**，localStorage 里已有 306 条空壳题目记录（全部 status/note/fav 为空）。影响：导出备份永远含 306 条空记录；"空用户"不可复现。修法：`rec()` 拆出只读版 `peek()` 供统计使用。

**N9 pagehide 用该标签页内存态整体覆盖 localStorage**
`app/js/app.js:110-116` 的 `flush()` 无条件 `Store.saveNow()`，`saveNow` 整包重写 `aiiv:records`。
实测：在页面外直接改 localStorage（模拟另一标签页写入），刷新后该写入被覆盖消失。
影响：多标签页同时打开会互相覆盖；单标签页使用不受影响。

**N10 专项 DOM id 双重前缀 `drill-drill-*`**
`views-knowledge.js:786` 渲染 `id="drill-${drillId}"`，而 `drillId` 已是 `drill-5fix02` → 实际 id 为 `drill-drill-5fix02`。
`views-knowledge.js:433` 的 `getElementById('drill-' + focusDrill)` 恰好同构，所以功能正常 —— 但这是"两边都多写一次前缀"的巧合式自洽，任何一边单独修正都会立刻打断深位定位。建议只保留一处前缀。

**N11 importRecords 与 importFull 的题目合并逻辑整段复制**
`store.js:554-604` 与 `store.js:781-824` 是同一段约 50 行逻辑的两份拷贝。N2/N5 的规则若要修，必须两处同改，漏改一处就会产生双写漂移。建议抽成 `mergeQuestionRecords(merged, incoming)`。

**N12 reviewReasons 同刻语义未文档化、无测试**
本地与备份 `_updatedAt` 相同时，本地胜（`store.js:589-598`），该规则没写进任何用户可见文案，也没有测试覆盖。行为本身可辩护，但与本轮「整套覆盖」的对外说法之间存在解释落差。

**N13 备份中的阅读位置在本地已有 docPos 时不会被恢复**
`store.js:489-492`：仅当 `!merged.ui.docPos || !merged.ui.docPos.docId` 才采用备份值。若本地已记录过别的文档位置，备份里的阅读位置静默丢弃。影响很小（只丢一个滚动位置），但属于"完整备份不完全"。

**N14 drill-1fix02 参考中间一句自相矛盾**
参考原文：「…第二轮同一个词 get(w, []) 拿到的是默认值新列表,append 后写回 len=2——单元素词没问题?不,真正崩在第二轮:get 拿到的是上次写入的 int 1…」
前后半句互相否定，像是把草稿推理痕迹留在了成品里。**结论正确**（实测 `count_words(['x'])={'x':1}`；`count_words(['x','x'])` 抛 `AttributeError: 'int' object has no attribute 'append'`），只是表述会卡人。
