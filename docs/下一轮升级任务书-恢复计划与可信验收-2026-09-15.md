# 下一轮升级任务书：恢复计划与可信验收

本文件可全文交给编码代理执行。依据[ec4b327审查报告](审查报告-ec4b327.md)，审查基线为`ec4b3270f435a0974fd1dc852a2ab9b7ac12f435`。如果开始执行时有更新提交，先确认已关闭项目，保留更新成果。

## 大方向

将网站推进为**操作结果可预知、学习记录可恢复、讲解经得住追问的面试工作台**。本轮最有价值的升级集中在三条主线：

1. **恢复计划成为真实契约。** 用户看到的预览，必须是将要执行的那份恢复结果，能说明改了什么、为什么改、哪些保持。
2. **测试能够证明承诺。** 暂停、同时间戳、关闭和冲突这些条件必须真实发生；测试既验证正式记录，也验证用户的未提交输入。
3. **内容质量以理解为标准。** 55题长度清单已完成，接下来逐题核对考点、因果和反例；把“字段够长”升级为“用户能够解释并迁移应用”。

先完成恢复与验证缺陷，再扩展学习体验。保持349道题的现有题号、Pi Agent分类、LangChain分类、个人记录和既有导入协议。

## 执行约定

你负责检查代码、复现、修复、测试、文档、提交推送及发布核验。按照下面阶段连续推进，不以给出建议或局部补丁结束。每个阶段形成可审查的完整结果；发现与目标直接相关的缺陷，补证据后一起处理。

- 所有破坏性场景、备份导入、清空和浏览器故障注入使用隔离测试数据，不操作真实学习浏览器。
- 不删除旧学习记录，不为解决合并问题批量更换题号、追问ID或会话ID。
- 预览与取消不写盘，失败不假报成功。确认前提供真实结果，而不是数量估计代替变更说明。
- 不降低内容阈值、不删除失败断言、不用通用段落补长度，不将提醒0解释为事实全面核查。
- 不复写别人的未提交修改，不强推远端。提交前后记录准确SHA，测试计数来自执行输出。
- Anki桌面、真实读屏、低端设备等无法执行的验证保持未验证；继续完成其余独立工作。

## 阶段0：将审查结果转成失败用例

1. 记录当前HEAD、远端HEAD、工作区改动、当前测试清单和审查对象。不要机械复制803作为新测试数量。
2. 复现MR-01：本地项目运行列表为空，备份有合法无runId旧记录；界面不能误判没有可恢复内容。
3. 复现MR-02：同runId备份更新正文，预览必须显示覆盖，而不只是“无新增”。
4. 复现ST-01：两个正常应用页，相同`_updatedAt`、不同值，顺序写入后检查两页、磁盘、重开是否一致。
5. 将暂停场景补成真正的旧内存场景；将关闭场景补成真正检查冲突输入副本的场景。
6. 保存当前失败证据。对尚未稳定复现的猜测，继续缩小情境，不直接宣布缺陷已修。

**交付物：** 最小失败用例、固定输入、预期与实际结果、准确复现命令。临时脚本必须放在明确的证据目录，不能假装已经纳入CI。

## 阶段1：建立统一的恢复计划生成器

1. 梳理普通记录备份、完整备份、旧版本备份和题库资料备份的解析与迁移路径，列出共同部分和各自范围。
2. 把外壳校验、记录规范化、旧项目runId迁移、旧专项尝试迁移、终态合并、冲突副本合并和字段差异计算收进统一入口。
3. 输入是本地基线与备份，输出是恢复计划：备份指纹、基线版本、规范化内容、准备写入的结果，以及每个实体的变化与原因。
4. 计划生成不得修改当前Store、传入备份对象或磁盘。迁移产生的身份必须稳定，不能在预览、确认两次计算中各生成不同随机ID。
5. 预览和正式导入共用同一份计划。不要继续在两个函数里复制merge调用，再靠人记得同步迁移步骤。
6. 普通记录和完整备份都应用相同的记录语义；完整备份再补题库、资料的计划，不能继续只统计输入文件数量。
7. 明确`noChanges`含义：只有最终准备提交的持久数据确实不变，才允许显示无需恢复。元数据、时间戳、默认空容器与实际业务变化分别处理。

**验收：** 新旧备份、缺runId、旧drillTries、终态、冲突副本、空值撤销、重复导入均通过。预览计划与执行后的数据语义一致，原对象和磁盘在预览后保持不变。

## 阶段2：让恢复预览真正可审阅

1. 按实体列出变化：题目记录、模拟轮次、未完成会话、终态、专项尝试、项目运行、口述草稿、冲突输入、阅读位置、扩展题库和导入资料。
2. 每个实体至少支持新增、更新、清空、保留、冲突待处理等状态。记录条数与字段变更条数区分显示。
3. 展示稳定ID、易读名称、前后摘要及采用原因。长正文默认折叠，允许打开完整前后文本；避免为了缩短UI隐藏重要覆盖。
4. 项目记录更新不再写成单纯“无新增”；草稿终止、SRS撤销、收藏取消等负向变化必须可见。
5. 给重要类别提供过滤和搜索。用户能直接找到某题笔记或某次项目运行，而不是阅读整个备份JSON。
6. 清楚解释主动恢复旧备份与接收过时标签页事件的不同意图；预览需要说明哪些清空或终态边界仍保留。
7. 取消后状态不变；无法恢复的条目给出具体原因与可保留原文件的方式，不说整份“没有变化”。

**验收：** 用真实文件选择器走流程；预览中看到的ID、旧值、新值和分类，与最终结果逐项对应。窄屏、键盘和长文本仍可操作。

## 阶段3：确认时验证计划没有过期

1. 预览绑定明确的本地基线版本和备份指纹，确认执行的是这份计划。
2. 预览期间另一页修改记录、用户撤销状态或发生清空时，旧计划应被标记过期；重新计算并展示差异，不能悄悄换一份结果执行。
3. 校验完整通过后再进入写入阶段，记录、题库和资料失败时保持可解释的回滚或恢复状态。
4. 写盘失败保留待恢复内容及原文件，允许重试；重试前再次检查计划基线，不能绕过过期检查。
5. 明确当前同步localStorage方案能提供的保证。版本检查不是自动获得跨进程原子事务，避免在文档里夸大。
6. 如果需要异步协调，将所有依赖同步返回值的入口列入迁移清单，以保存中、成功、失败状态替代伪同步成功。逐条验证重试、清空和pagehide路径。

**验收矩阵：** 预览→对页改笔记→确认；预览→对页清空→确认；预览→取消；预览→配额失败→恢复空间→重试；完整备份后续键写入失败；重复点击确认。不能出现未经审阅的覆盖或重复恢复。

## 阶段4：重建可信的并发矩阵

1. 每个测试先检查前置条件。暂停时先证明B仍有旧内存、没有处理目标事件，再恢复；同毫秒测试先证明两个记录时间戳相同且值不同。
2. 正常路径使用真实Store接口；直接写localStorage用于注入特殊情况时，明确说明这是故障或旧客户端模拟，不作为正常写入协议的替代。
3. 删除无人读取的暂停标记。浏览器回调只访问浏览器环境，不能在里面调用Node侧`page.evaluate`变量。
4. 不吞掉等待异常继续检查其它条件。等待失败时保存当前内存、磁盘、事件轨迹和失败原因，直接标记该场景失败。
5. 对每个场景检查A内存、B内存、磁盘、重开四态；不需要的状态要说明原因，而不是在交付文档中统一声称已经检查。
6. 同一输入交换A/B、交换事件到达顺序并重复运行，检查结果是否依赖先后位置。固定种子应真正驱动操作生成，并记录种子和操作序列。
7. 关闭前保存场景，检查当前schema的`noteDraft`和输入副本正文；关闭原页后，通过新页面和备份往返证明内容仍可找回。
8. 给测试加反向验证：临时阻断合并、去掉副本保存或改错决胜规则时，对应测试必须失败。完成后还原所有故障注入。

**交付物：** 可重放矩阵、原始事件轨迹、各场景真实前置条件、四态断言、反向验证结果。测试名称、注释、机器报告和交付文档的覆盖范围一致。

## 阶段5：定义同时间戳与部分记录的合并规则

1. 明确同一题目不同字段、同一字段不同值、明确清空、默认空值和缺失字段分别意味着什么。
2. 给相同时间戳定义稳定决胜依据，或保留为显式冲突；不能让每一页都无条件保留自己的本地值，却宣称收敛。
3. 检查合并的幂等性、输入交换后的结果以及事件重排后的结果。对合法记录组合做属性测试，特别覆盖旧备份缺字段。
4. 让磁盘新鲜度检测与写入入口使用同一套规则。记录导入、普通保存、清空和终态不能各自维护不同的“新者胜”。
5. 对完全同时写入的边界保持明确。如果当前目标只保证顺序和常规双页，则界面、文档和测试都按这个范围表述；需要更强保证时再依据测量选择协调方案。
6. 不为通过同毫秒测试丢弃未冲突的字段、个人输入副本或历史记录。

**验收：** ST-01四态分歧关闭；对称输入、相同时间戳、空值撤销、部分记录补齐、旧页恢复和同会话终态均有独立断言。

## 阶段6：对55题做语义验收

1. 从实际JSON语义diff生成按ID的审查表：原缺口、新增知识点、考点关联、反例或推导、依据与状态。缩进变化不能计作内容深化。
2. 优先修复AD-001、AD-002的误区错配，核对它们与AG-001/AG-002的重复关系。保留真正有价值的跨题联系，但写明联系，不整句搬运。
3. 修复PI-025：区分供应商提示缓存、应用上下文整理、结果或语义缓存；费用、延迟、输入改变和答案质量分别解释。
4. 修复AD-004：固定seed用于重现，同组多个seed用于候选配置的配对比较。说明不同环境和非确定性算子的边界，不把一次微调结果当成普遍规律。
5. 检查AG-010“需求过半用框架”等新阈值，改为关键约束和可验证取舍，避免凭比例替用户做架构决定。
6. 对本批所有新增误区，逐条检查能否给出本题相关的错误例子及正确解释。条数达标但说的是别的题，仍未完成。
7. 使用原始适配输入生成native与manifest；保留哈希保护，确保题号、追问身份和学习记录稳定。
8. 不能只修审查指出的几句就宣布55题全面通过。完整记录每题的语义验收状态、证据和未核查部分。

**交付物：** 55题语义验收表、修改前后差异、来源依据及剩余问题。真实训练或SDK运行没有执行时如实标注。

## 阶段7：正确处理剩余21项提醒

1. 重新跑审计，按当前结果工作。本轮基线为9项量化表述提醒、12项相对总长提醒，不是21项全部偏薄。
2. 量化提醒逐条分为可复算算术、明确教学假设、来源实验和未经验证的经验建议。算术就复算，实验就记录条件，没有证据的经验比例不要只加“约”字。
3. 相对分位会随全库变化，不将它机械当作必须清零的缺陷。优先补真实缺少的因果、反例和边界；内容已清楚时记录保留理由。
4. 固定长度清单、内容审计、来源核查、人工语义验收分开报告，各自说明检测能力。
5. 报告自动统计suite名称和数量，工具自检与测试用例分开，防止漏掉缓存戳和学习完整性等既有套件。

**完成条件：** 每条提醒有可解释处置，状态表与原始输出一致；不以全零数字代替内容质量。

## 阶段8：在可靠性通过后提升学习效果

1. 让一轮练习结束后产生下一步建议：哪些概念没讲清、哪些追问没答、应该回到哪道题或哪段文档。建议基于真实回答与用户自评，区分事实和推断。
2. 加入可选的口述检查流程：先给题干，再计时表达，再按评分点自检，最后安排复习。计时和展开参考不能自动算作掌握。
3. 用已保存的题面和参考快照比较同题两次回答，突出新增要点、仍缺条件和用户自评变化，避免对自由文本打不可靠的精确分数。
4. 让历史检索、追问定位、表达卡与复习队列相互连接；一次搜索应能回到真实作答位置，再继续新的尝试。
5. 先完成一个专题的小闭环并让流程可验收，再推广到所有分类。保持Pi Agent的评分与追问结构，避免为了统一UI丢掉信息。
6. 不以自动评价模型替代证据规则。若将来接入外部模型，另行定义来源、数据发送范围、失败与成本边界。

**验收：** 用户完成一轮后能看到基于本轮记录的下一步行动，能重新练、能比较、能带走材料；未作答、未自评和仅查看参考不会被算作完成证据。

## 阶段9：发布与交付

1. 运行新增失败用例及相关回归，再运行完整测试；计数按最新执行结果生成。
2. 检查数据schema、去重、两个适配器、来源结构、构建一致性与缓存戳。保留实际离线访问和真实下载测试。
3. 完整走一遍新用户旅程与老备份旅程：作答→追问→保存→跨页→导出→清空→预览恢复→确认→检索历史。
4. 交付文档列出每项问题的关闭证据，区分修复、未验证、明确不支持。Anki桌面和真实设备未运行的部分不得用字符串断言替代。
5. 分阶段提交，推送前检查远端更新，随后核对完整SHA的CI、Pages及线上文件。远端失败必须继续处理，不能只给本地通过结果。
