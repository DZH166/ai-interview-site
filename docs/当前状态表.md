### 3.1 记录层(Node 回归 5 通过 / 10 失败)

| 编号 | 缺陷 | 严重度 |
| --- | --- | --- |
| B-1 | 更新的项目草稿备份**只恢复第一个字段**,后续字段静默丢弃,却仍把 `updatedAt` 抬到备份时间——此后更正确的备份也会被拒 | 高 |
| B-2 | 用户主动清空的字段被**更旧的**备份复活 | 高 |
| C | 旧版(无 `runId`)项目运行记录在恢复时被**静默丢弃** | 高 |
| E-4 | 「待消化专项」取数组末位当最新,顺序被打乱时把已解决的专项又拎回来 | 中 |
| F | 已保存的项目运行记录与项目草稿**不进全文索引**,搜不到 | 中 |
| H-1 | `tests/behavior-tests.js:524` 是恒真断言(`... \|\| true`),该用例从未真正校验 | 中 |
| H-2 | 「清空全部记录」后检索索引未失效,仍能搜出已清空的笔记与尝试 | 中 |

B-1 的实测观测:本地草稿字段顺序为 `runOutput, updatedAt, debug, todo`;
恢复一个 `updatedAt` 更新的备份后得到
`{runOutput:"备份新输出", updatedAt:9000, debug:"本地旧定位", todo:"本地旧待办"}` ——
即**混合状态**:一部分来自备份、一部分来自本地,而时间戳声称是备份的。

### 3.2 界面层(浏览器复现 3 通过 / 8 失败)

| 编号 | 缺陷 | 严重度 |

### 3.3 项目C 四层诊断(11 失败)

接口缺失:`retrieve` / `generate` / `validate` / `diagnose` / `coverage_oracle` / 固定 `CONFIG` 都不存在,
四层归因无法被测试、也无法被单元验证。

| 编号 | 缺陷 | 严重度 |
| --- | --- | --- |
| G-1 | 「库里到底有没有」由**查询关键词表**判定,与库内容无关:向库中加入 `公司地址` 文档后,`公司地址在哪里?` 仍被判「库中没有」 | 高 |
| G-2 | 库外主题(公司年会 / 比特币支付 / 改绑手机号)被归因成第②层「改进检索而不是补文档」——把学习者引向错误方向 | 高 |
| G-3 | 第③层**没有检测器**:源码中不存在任何 `layer: 3`;证据被 `top_k=1` 裁掉一半后仍判为正常 | 高 |
| G-4 | 第④层「校验」只看 `broken_fake` 开关;单证据时故意忽略证据的回答被**放行**(`layer=0, refused=false`) | 高 |
| G-5 | 0 分文档被当作「候选证据」展示(`候选[d1,d2]` 实际都是 0 分),评测表看起来有召回 | 中 |
| G-6 | 同一查询同一库,层级随调用方手调的 `refuse_threshold` 在 0/2/2 之间跳;`main()` 里逐题硬编码阈值来摆出叙事 | 高 |
